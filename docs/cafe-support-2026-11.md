# 카페·디저트 키워드 지원 — 정확도 대조 (2026-11)

## 배경
2026-11-16까지 `카페|커피|디저트|베이커리|빵집|브런치` 라는 **단어 목록**으로 플레이스 등록을
막고 있었다. 비바구스토(해운대, 양식)가 "해운대 브런치"를 등록하려다 거부된 게 오탐으로 드러나,
단어 판정을 없애고 **실제 목록 페이지가 열리지 않을 때만**(HTTP 4xx) 안내하도록 바꿨다.
`/cafe/list`는 404지만 **`/restaurant/list`가 카페·디저트 업종까지 같이 돌려준다**(실측).

그래서 이제 순수 카페 키워드("해운대 카페")도 등록·수집된다. **쓸 만한 목록인지**를 확인하기 전까지는
"지원한다"고 말하지 않기로 했다. 이 문서가 그 확인 기록이다.

## 확인 항목
1. **0곳이 나오는지** — 0곳은 저장되지 않고 보류로 빠지므로, 자주 나오면 지원 불가다.
2. **같은 키워드 두 번 조회 시 상위 10곳이 일치하는지** — 회차마다 목록이 바뀌면 순위 추적 자체가 성립하지 않는다.
3. **캡처된 GraphQL 연산자 이름이 허용 목록(`LIST_OPS`)에 있는지** — '신규 오픈' 모듈을 순위로
   저장한 2026-10-30~11-09 오염(1,199건)의 재발 감시.
4. **실제 네이버 화면 순서와 일치하는지** — 사장님이 보내 주는 지도/앱 검색 캡처와 대조한다.
   **서버에서 naver.com 화면에 접근하지 않는다**(크론 IP 보호).

## 요청 상한 (네이버 요청 예산)
| 항목 | 값 |
|---|---|
| 대조 키워드 | 5개 (해운대 카페, 해운대 디저트, 광안리 카페, 동래 카페, 수원 카페) |
| 키워드당 회차 | 2회 |
| **하루 요청 상한** | **12건** (5×2 + 여유 2). 도구에 하드코딩된 상한이라 넘을 수 없다 |
| 요청 간격 | 60초 |
| 조회 깊이 | 상위 30곳 (딥스캔 300 아님 — 상위 10곳 비교에 충분) |
| 실행 시각 | **KST 02:10** (심야). 02:00 이전·05:30 이후에는 시작하지 않는다 |
| 저장 | **없음.** DB 쓰기 호출이 도구에 존재하지 않는다 |
| 유효기간 | `EXPIRES = 2026-11-20`. 지나면 `--force` 없이 돌지 않는다 |

블로그 순위 확인 도구(`blogrank_probe.mjs`)는 **별도 예산 4건**(최신순 1 + 관련도순 1 + 운영 경로 1 + 여유 1).

안전장치는 둘 다 같다: 심야 시간대 밖이면 시작 안 함, `collect.mjs`/`collectPlace.mjs`가 돌고 있으면
즉시 중단, 05:30 넘으면 남은 조회 취소(05:50 pm2 재시작·06:00 수집 전에 비운다).

## 도구
```bash
# 카페류 대조 (심야 전용, 저장 없음)
node tools/cafe_compare.mjs
# 결과: /var/log/blog-rank-scraper/cafe-compare-<날짜>.txt / .json

# 블로그 순위 불일치 확인 (심야 전용, 저장 없음)
node tools/blogrank_probe.mjs --keyword="해운대 연말모임" --store=4
# 결과: /var/log/blog-rank-scraper/blogrank-probe-<날짜>.txt / .json
```

## 회차마다 목록이 달라지는 경우 — 원인 가설과 걸러내는 설계안 (구현 보류)

**가설 1 — 네이버의 모듈 교체.** 리스트 페이지는 '순위 목록' 말고도 '신규 오픈', '요즘 많이 찾는'
같은 모듈을 같이 띄운다. 회차에 따라 어느 모듈의 GraphQL이 먼저 뜨는지가 달라지면 전혀 다른 목록이
잡힌다. 2026-10-30~11-09 오염이 바로 이 경우였다(`getOpeningRestaurants`). → **연산자 이름 허용
목록으로 이미 막혀 있다.** 대조에서 (c) 항목이 이 가설의 측정값이다.

**가설 2 — 개인화·A/B 테스트.** 같은 쿼리에 대해 좌표·세션·실험군에 따라 다른 순서를 준다.
카페류는 '분위기·저장수' 같은 신호가 많아 식당보다 흔들릴 여지가 크다.

**가설 3 — 동률 구간의 비결정적 정렬.** 상위권은 고정이고 중하위권만 섞인다면 이쪽이다.
→ 상위 5곳은 같은데 상위 10곳이 다른 패턴으로 구분된다.

**설계안(저장 전 일관성 검사).** 셋 중 어느 가설이든 "한 번 보고 저장"이 위험하다는 결론은 같다.

1. **두 번 조회 → 상위 5곳이 같은 순서일 때만 저장.** 간격 20~30초.
   - 불일치면 그날은 **저장하지 않고 보류**(기존 0곳 보류와 같은 취급) — 가짜 순위를 남기지 않는다.
   - 비용: 카페류 키워드만 요청이 2배. 전체 키워드로 넓히면 수집 시간이 2배가 되니 **카페류에만** 적용.
2. **판정 기록.** `place_rankings`에 저장할 때 `verify: 'double'` 같은 표시를 남겨,
   화면에서 "2회 확인된 순위"와 "1회 측정"을 구분할 수 있게 한다.
3. **연속 불일치 감시.** 같은 키워드가 3일 연속 불일치면 그 키워드는 자동으로 추적에서
   **쉬게 하고 알림만** 보낸다(자동 삭제는 하지 않는다).
4. **적용 범위 판단은 대조 결과를 보고.** 5개 중 2개 이상이 상위 5곳까지 흔들리면 카페류는
   **지원하지 않는 쪽**이 맞다. 상위 5곳은 고정이고 6~10위만 흔들리면 1번 설계로 충분하다.
