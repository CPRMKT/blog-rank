# 플레이스 순위 자체 백업·감시 설계 (2026-11-21, 설계만 — 미적용)

배경: Supabase 자동 백업은 하루 한 번(15:29 UTC)·보존 7일이다. 2026-11-14 사고는 **백업 4시간 전**에
일어났고, 쓸 수 있던 전날 백업은 알아차리기 전에 보존 기한이 끝났다
([place-loss-final-2026-11.md](place-loss-final-2026-11.md)). 두 가지가 필요하다 —
**① 우리 손에 있는 사본**, **② 사라진 걸 하루 안에 알아차리는 감시.**

## A. 일일 증분 백업

### 무엇을, 언제
- **저녁 수집이 끝난 뒤**(`collectPlace.mjs` 저녁 회차의 완료 줄 다음) 그날 `checked_date = 오늘` 인
  `place_rankings` 행 전체를 받아 파일 하나로 쓴다. 아침 회차 뒤에도 한 번 쓰고 저녁에 덮어쓴다
  (저녁 회차가 실패해도 아침분은 남는다).
- 받는 경로: 기존 API(`/api/db`, 크론 시크릿)에 **읽기 전용 액션 `export_place_day`** 를 추가 —
  `supaFetchAll` 로 1,000행 절단 없이 받는다. 서버에 DB 비밀번호를 새로 두지 않는다.
- 추가로 **전날 파일을 한 번 다시 떠서 비교**한다(아래 무결성).

### 파일
```
/var/backups/blog-rank/daily/place_rankings_2026-11-21.jsonl.zst     ← 한 줄 = 한 행
/var/backups/blog-rank/daily/place_rankings_2026-11-21.meta.json     ← 행 수·키워드 수·sha256·만든 시각
```
`meta.json` 예: `{"date":"2026-11-21","rows":25365,"keywords":376,"sha256":"…","made_at":"…","source":"evening"}`

### 용량 (실측 기반)
기존 백업 파일(22,333행)로 쟀다: 원본 7.08MB → **gzip 0.58MB(12배)** → **zstd -19 0.22MB(32배)**.

| | 하루(약 25,000행) | 90일 |
|---|---:|---:|
| zstd -19 | **약 0.25MB** | **약 22MB** |
| gzip -9 | 약 0.65MB | 약 59MB |

서버 디스크: 9.8GB 중 **여유 1.8GB(82% 사용)**. 90일 22MB 는 여유의 1.2% — 용량 걱정은 없다.
오히려 위험은 디스크가 다른 이유(로그 29MB·브라우저 캐시)로 차는 것이므로, **여유가 500MB 밑이면
백업 스크립트가 경고**를 내게 한다.

### 보관
90일. 91일째 파일은 **삭제 전에 meta 의 sha256 을 다시 대조**하고 지운다(`find -mtime` 로 무조건 지우지 않는다).

### 무결성
1. 쓰고 나서 **다시 읽어** 행 수 = meta.rows = DB `count(*) where checked_date=그날` 인지 확인.
2. 다음 날, **전날 날짜를 DB에서 다시 세어** 파일의 행 수와 비교 → 줄었으면 **그게 곧 사고 신호**다(B와 연결).
3. sha256 을 meta 에 남겨 파일 손상을 잡는다.

### 복원 절차
```
node tools/place_daily_backup.mjs --restore=2026-11-21 --dry      # 파일 행 수·키워드 수와 DB 현재 상태 비교만
node tools/place_daily_backup.mjs --restore=2026-11-21 --only-missing   # DB에 없는 (키워드,날짜) 쌍만 넣는다
```
- **없는 쌍만** 넣는다(있는 쌍은 건드리지 않는다) → 삭제가 필요 없어 가드와 충돌하지 않는다.
- 넣는 경로는 검증된 `save_place_rankings`(쌍 단위 원자적). 2026-11-21 에 16쌍 214행을 이 경로로 되살렸다.
- 계획서에는 **"복원에 쓸 파일의 시각"과 "사고 시각"의 선후**를 한 줄로 적는다.

### 서버 한 곳에만 두는 위험 — 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **1. 서버만** | 위 그대로 | 가장 단순, 비용 0 | 서버 디스크가 죽거나 서버를 실수로 지우면 같이 사라진다 |
| **2. 월 1회 사장님 PC로 복사** | 매월 1일 `scp` 로 `daily/` 폴더를 내려받기(약 7MB/월). 명령 한 줄을 docs 에 둔다 | 비용 0, 완전히 다른 장소 | 사람이 해야 한다 — 잊으면 끝. 최대 한 달치 공백 |
| **3. 매일 클라우드 저장소로** | 서버에서 매일 Supabase Storage(비공개 버킷) 또는 구글 드라이브로 올림 | 자동, 매일, 다른 장소 | Supabase Storage 는 **같은 프로젝트에 묶인다**(프로젝트 사고에 같이 노출). 드라이브는 인증 설정 필요 |
| **4. cpr-marketing-os 의 `rank_history`** | 아래 따로 비교 | 이미 만들어져 매일 07:00 돈다 | **우리 매장 순위만** 담는다 — 아래 |
| **권고: 1 + 2** | 서버 일일 백업 + 월 1회 PC 복사 | 돈·새 인증 없이 장소가 둘 | 월 1회 수동 |

### `rank_history` 를 append-only 사본으로 쓰는 안 (사장님 추가 요청)

현재 상태(cpr-marketing-os 저장소 기준): `004_rank_history.sql` 적용 완료, n8n 워크플로우
`sync-blogrank-rankings` 가 **매일 07:00 KST** 에 읽기 전용 역할 `cprmkt_readonly_sync` 로
blog-rank 의 최근 7일 순위를 읽어 **upsert** 한다. **연결된 계약이 없어 지금 0행**이다.

| | 서버 일일 백업(A) | `rank_history` |
|---|---|---|
| 담는 것 | 그날 **전체 행**(키워드별 상위 300곳: 이름·업종·리뷰·저장수) | **계약에 연결된 우리 매장의 순위 숫자 한 줄**(계약·종류·키워드·순위·날짜) |
| 하루 분량 | 약 25,000행 | 계약 매장 × 키워드 수 (수백 행) |
| 순위 추적 카드(우리 순위) 복원 | ✅ | ✅ **(계약 연결된 매장만)** |
| 날짜 비교 탭(경쟁 매장 목록) 복원 | ✅ | ❌ 경쟁 매장 행이 없다 |
| 리뷰·저장수 이력 복원 | ✅ | ❌ 칼럼이 없다 |
| 계약 없는 매장 | ✅ | ❌ **계약(`blogrank_place_id`) 매핑이 있어야 적재된다** |
| 장소 | blog-rank 스크래퍼 서버 | **다른 Supabase 프로젝트** — blog_rank DB 사고와 완전히 분리 |
| 원본에서 지워지면 | 파일은 그대로 | **그대로 남는다** (upsert 는 지우지 않는다) |
| 원본 값이 바뀌면 | 그날 파일은 고정 | **최근 7일 안이면 덮어쓴다** — 엄밀한 append-only 는 아니다 |
| 블로그 순위 | (대상 아님) | ✅ 같이 담는다 |
| 추가 작업 | 스크립트·액션 신규 | **계약 매핑만 채우면 내일부터 쌓인다** |
| blog-rank 에 주는 부담 | 하루 1~2회 읽기 | 이미 돌고 있음(0) |

**판단: 둘은 대체가 아니라 보완이다.**
- `rank_history` 는 **가장 값진 한 줄(우리 매장 순위)을 다른 프로젝트에** 두므로, 이번 같은 사고에서
  순위 추적 카드는 되살릴 수 있었다. 계약 매핑만 채우면 되니 **가장 싸게 얻는 두 번째 장소**다.
- 하지만 전체 목록·리뷰·저장수는 못 살린다. **행 단위 복원은 A 만 가능하다.**
- "append-only" 로 쓰려면 한 가지를 정해야 한다: 지금은 최근 7일을 덮어쓴다. 원본의 **오염이 7일 안에
  사본으로 번지는** 것까지 막으려면 `on conflict do nothing` 으로 바꿔야 하는데, 그러면 저녁 재수집으로
  고쳐진 값이 반영되지 않는다. → **덮어쓰기는 두되 "3일 지난 날짜는 건드리지 않는다"** 가 절충안이다
  (cpr-marketing-os 쪽 변경이라 그쪽 창에서 결정).

## B. 일별 행 수 감시

### 기록
매일 저녁 회차 뒤, **최근 14일**의 일별 행 수·키워드 수를 한 번에 세어 서버 파일에 한 줄 추가한다.
```
/var/log/blog-rank-scraper/place-daycount.jsonl
{"at":"2026-11-21T22:31+09:00","counts":{"2026-11-21":[25365,376],"2026-11-20":[23068,364], …14일}}
```
세는 방법: 읽기 전용 액션 `place_day_counts`(날짜별 `count`·`count(distinct keyword)`). DB 표를 새로 만들지 않는다
(감시 기록까지 같은 DB 에 두면 같이 사라질 수 있다).

### 판정
오늘 센 값을 **어제 기록**과 날짜별로 비교한다. **오늘 날짜는 제외**(수집 중이라 늘어난다).

| 조건 | 판정 |
|---|---|
| 과거 날짜의 행 수가 **5% 이상 감소** | 🔴 경보 |
| 과거 날짜가 **통째로 0** | 🔴 경보 |
| 키워드 수가 5% 이상 감소 | 🔴 경보 |
| 증가(백필·복원) | 기록만 |
| **승인된 삭제** | 감사 표(`place_rankings_delete_audit`)에 같은 날짜의 기록이 있으면 경보 문구에 "감사 기록 있음: 사유 …" 를 붙인다 — 숨기지는 않는다 |

2026-11-14 사고에 적용하면: 그날 22:30 회차 뒤 비교에서 **16개 날짜가 0** → 당일 밤 경보.
11/13 백업의 보존 기한(11/21 00:29 KST)까지 **6일의 여유**가 있었다.

### 알림
- **배너**: 서버가 `place-daycount-alert.json` 을 쓰고, 관리자 화면이 기존 상태 조회에 실어 빨간 배너로 띄운다
  ("⚠ 과거 순위 기록이 줄었습니다: 10/26 25,802 → 0 외 15일"). 관리자에게만 보인다.
- **텔레그램**: 기존 `notify.mjs` 로 보낸다. **토큰이 없으면 휴면**(지금 상태) — 배너와 로그는 그대로 동작한다.
- 같은 경보는 하루 한 번만. 해제는 수동(확인 버튼) — 자동으로 사라지면 놓친다.
