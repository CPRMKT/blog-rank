## 3. 새 프로젝트에서 읽을 쿼리 (절단 없음)

Supabase MCP `execute_sql` 는 서비스 권한으로 돌아 **RLS·1,000행 상한을 거치지 않는다.**
PostgREST 를 쓸 때만 `supaFetchAll` 식 limit/offset 페이징이 필요하다.

먼저 읽기 전용 확인:
```sql
-- (1) 일별 행 수·키워드 수 — 10/15~11/14
select checked_date, count(*) as rows, count(distinct keyword) as keywords
from place_rankings
where checked_date between '2026-10-15' and '2026-11-14'
group by checked_date order by checked_date;

-- (2) 사라진 창의 총계
select count(*) as rows, count(distinct keyword) as keywords,
       count(distinct checked_date) as days, min(id) as min_id, max(id) as max_id
from place_rankings
where checked_date between '2026-10-26' and '2026-11-10';

-- (3) 스키마·인덱스가 운영과 같은지
select column_name, data_type, is_nullable
from information_schema.columns
where table_schema='public' and table_name='place_rankings' order by ordinal_position;
select indexname, indexdef from pg_indexes
where schemaname='public' and tablename='place_rankings' order by indexname;
```

## 4. 옮기는 방법 — 두 가지

**A안 (권함): 운영에서 `dblink` 로 직접 끌어온다.**
운영 DB에 `dblink` 1.2 또는 `postgres_fdw` 1.1 을 쓸 수 있다(설치 가능, 아직 미설치).
한 번의 SQL 로 날짜별 삽입이 끝나고, 13만 행이 중간 경로를 타지 않는다.
- 필요한 것: 새 프로젝트의 DB 접속 정보(사장님이 직접 넣어 주셔야 한다. 화면에 찍지 않는다)
- 운영에 `create extension dblink` 가 필요하다 → **쓰기이므로 승인 뒤에만.** 끝나면 `drop extension`.
- 원래 id 는 쓰지 않는다: `insert into place_rankings (keyword, checked_date, rank, place_id, name, category, visitor_reviews, blog_reviews, saves, created_at, owner_id) select ...` — `id` 는 시퀀스가 새로 부여.

**B안: MCP 로 날짜별로 읽어 서버에서 밀어 넣는다.**
접속 정보가 필요 없다. 대신 13만 행이 조각나서 오가므로 느리다(날짜 16회 × 조각).
- 새 프로젝트: `execute_sql` 로 TSV 한 칼럼으로 묶어 읽음
- 운영: 스크래퍼 서버의 기존 service key 로 REST 배치 삽입(쌍 단위, 500행씩)

둘 다 **쌍 단위로 진행하고 배치마다 삽입 행 수를 확인**한다.

## 5. 절차 (승인 뒤)

1. 운영의 10/26~11/10 행 수가 **0인지 재확인.** 0이 아니면 중단·보고.
2. 날짜 하나씩: 제외 쌍을 뺀 행을 읽어 삽입 → 그 날짜 행 수·키워드 수 확인 → 예상값과 비교.
3. 16일 전부 끝나면 전후 일별 표를 SQL 로 다시 떠서 첨부.
4. 같은 재현율 기준으로 10/26~11/10 **전 키워드 재판정.** A/B 등급이 남으면 **삭제하지 않고 목록만 보고**하고 승인을 받는다.
5. 화면 확인: 석촌 쭈꾸미(11/09 등), 아름동 오징어 등 복원 날짜가 순위로 보이는지 캡처.
6. 새 프로젝트에는 **쓰기 금지.** 검증이 끝나면 사장님이 삭제해 과금을 멈춘다.

## 6. 곁다리 — FK·트리거·캐스케이드 조사 (읽기 전용, 2026-11-21)

### 조회 결과

| 항목 | 결과 |
|---|---|
| place_rankings 가 **거는** 외래키 | **1개** — `owner_id → profiles(id) ON DELETE CASCADE` |
| place_rankings 를 **가리키는** 외래키 | **0개** |
| 트리거(내부 제외) | **0개** |
| 규칙(rule) | **0개** |
| 상속·파티션 | **0개** |
| `stores` / `store_place_keywords` 와의 FK | **없음.** `keyword` 는 그냥 text 칼럼이다 |
| 소유자 분포 | **1명** — `246f38bc…`, 2,979,991행, 2026-07-22~11-20, **106일** |
| profiles 행 수 | **1행**, id 가 위 소유자와 같다 (= 지워지지 않았다) |

### 판정 — **cascade 로는 설명이 안 된다.** 근거 3개

1. **유일한 cascade 경로에 날짜 조건이 없다.** 지워질 수 있는 상위 행은 `profiles` 한 행뿐이고,
   그게 지워지면 그 소유자의 **297만 행 전부**가 같이 지워진다. 16일만 골라 지울 방법이 없다.
2. **그 profiles 행은 지금도 그대로 있다.** 같은 uuid 다. 지워졌다 다시 만들어진 거라면 살아남은
   10/15~10/25 행도 다시 넣어야 했을 텐데, 그 행들의 id 는 원래 시퀀스 구간(10/25 끝 5,467,117)에
   그대로 있다 — 재삽입된 흔적이 없다.
3. **매장·키워드를 지워도 순위 행은 건드려지지 않는다.** place_rankings 를 가리키는 FK 가 0개고,
   `keyword` 는 참조가 아니라 text 다. 트리거·규칙도 0개여서 간접 삭제 경로도 없다.

덧붙여 `106일`이라는 숫자가 증거 하나를 더 준다. 7/22~11/20 은 122일인데 106일만 남았다 —
**빠진 16일이 정확히 10/26~11/10 이다.**

→ 남는 가능성은 여전히 **사람이 날짜 범위로 실행한 `delete`** 다.
