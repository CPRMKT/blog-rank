`purge_place_rankings` 를 **전체 키워드 목록 × 10/26~11/10** 으로 호출했다.

```js
const kws = [...new Set(((tr && tr.result) || []).map(x => x.keyword))];   // ← 추적 중인 전체 키워드
const dates = []; for (let i=26;i<=31;i++) dates.push("2026-10-"+i);
                  for (let i=1;i<=10;i++)  dates.push("2026-11-0"+i);
dates.push("2026-11-10");
for (const d of dates) {
  const pairs = kws.map(k => ({ keyword: k, date: d }));
```

## 왜 이게 원인이라고 단정하는가 — 숫자가 세 번 맞는다

**① DELETE 문장 수가 정확히 맞는다.**
`pg_stat_statements` 의 purge 문장 호출 = **55회**.
세션 기록에서 확인한 `contam_cleanup --delete` 실행 = **38회**(아래 표).
호출 ① 이 돈 날짜 9개(10/26~11/03) + 호출 ② 의 8개 = **17회**. → **38 + 17 = 55** ✅

**② 지운 행 수가 한 행도 안 틀린다.**

## 왜 막히지 않았나 — 코드

`api/db.js` `purge_place_rankings` 가 읽는 옵션은 **`data.export` 와 `data.dry` 둘뿐**이다.
`count` 는 어디서도 읽지 않는다. **모르는 옵션을 거부하지 않기 때문에** 세기 의도가
삭제로 그대로 떨어졌다. 안전장치가 하나도 걸리지 않았다:

| 있었어야 할 장치 | 당시 |
|---|---|
| 모르는 옵션 거부 | 없음 → `count:true` 무시 |
| 삭제는 명시적 `confirm` 필요(기본 dry) | 없음 → 기본이 삭제 |
| 한 문장 행 수 상한 | 없음 → 한 문장에 25,802행 |
| 예상 행 수 선언·대조 | 없음 |
| 삭제 전 백업 강제 | 도구(`contam_cleanup`)에만 있고 **API 직접 호출에는 없음** |

**핵심은 마지막 줄이다.** 백업·dry·행수 대조는 전부 **도구 쪽**에 있었고,
API 액션 자체는 아무 조건 없이 지웠다. 도구를 거치지 않으면 보호가 0이었다.

## 앞선 보고 정정 2개

1. **"사람이 대시보드 SQL 편집기에서 날짜 범위로 delete 했을 것"** — 틀렸다.
   대시보드는 무관하다. 우리 API 를 통한 **쌍 단위 삭제(목록이 전체 키워드)** 였다.
   `pg_stat_statements` 에 날짜 범위 delete 가 없던 것과 모순되지 않는다.
2. **"11/14 의 16쌍 214행 복원은 실행되지 않았다"** — 틀렸다.
   **11/14 09:09:36 UTC 에 "복원 완료: 16쌍" 으로 실제 실행됐다.**
   그 214행은 약 2시간 뒤 호출 ①·② 에 같이 지워졌다. 내가 "복원 흔적이 없다"고 본 근거
   (옛 날짜에 11/11 이후 id 가 0개)는 **복원 안 됨**과 **복원 뒤 삭제됨**을 구별할 수 없었다.

## 복원과의 관계

이 사실은 복원 계획을 **더 쉽게** 만든다. 지운 주체와 범위가 정확히 특정됐기 때문에:
- 복원 대상 **133,140행**은 "내가 11/14 20:16·20:23 에 지운 행" 과 **같은 집합**이다.
- 오염 쌍(1,782쌍 / 29,493행)은 그보다 **먼저** 지워졌으므로 복원 대상에 애초에 없다.
- 즉 **"백업에서 10/26~11/10 전부를 가져와 제외 목록만 빼면" 정확히 복원된다.**
  별도 판정이 필요 없다.
