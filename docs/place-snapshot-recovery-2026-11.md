# n8n 스냅샷으로 10/26~11/10 되살리기 — 타당성 평가 (2026-11-21, 파일 도착 전)

출처: cpr-marketing-os 의 n8n 워크플로우 `sync-blogrank-rankings` 실행 기록(11/1~11/14, 매일 07:00 KST).
매 실행이 blog-rank 의 `place_rankings` **최근 7일 전체 행**을 `(place_id, keyword, rank, checked_date)` 로 읽어 갔다.

## 선후 관계 (먼저)
| | 시각 (KST) |
|---|---|
| 마지막 스냅샷 | **11/14 07:00** |
| 내가 지운 시각 | 11/14 20:16 · 20:23 |
→ **모든 스냅샷이 삭제보다 앞선다.** 11/14 07:00 스냅샷은 1차 오염 삭제(11/14 04:02) 뒤, 2차(12:09) 앞이다 —
오염 쌍은 어차피 제외 목록으로 빼므로 어느 스냅샷을 쓰든 결과가 같다.

날짜 D 의 "최종 상태"는 **D+1 ~ D+7 아침 스냅샷**에 들어 있다(D 당일 07:00 스냅샷은 수집 도중이라 덜 찼다).
| 날짜 | 담고 있는 스냅샷 |
|---|---|
| 10/26 | 11/01, 11/02 |
| 10/27 ~ 11/06 | 각각 2~7개 |
| 11/10 | 11/11, 11/12, 11/13, 11/14 |
| (검증용) 10/25, 11/11~11/13 | 지금도 DB 에 멀쩡 → **스냅샷이 DB 와 같은지 대조**에 쓴다 |

## 1. 표 구조 — 4개 필드만으로 넣을 수 있나

| 칼럼 | 타입 | NOT NULL | 기본값 | 스냅샷에 있나 | 넣을 값 |
|---|---|---|---|---|---|
| id | bigint | ✅ | 자동 증가 | — | 새 번호 |
| keyword | text | ✅ | — | ✅ | 스냅샷 |
| checked_date | date | ✅ | — | ✅ | 스냅샷 |
| rank | integer | | — | ✅ | 스냅샷 |
| place_id | text | | — | ✅ | 스냅샷 |
| owner_id | uuid | | `auth.uid()` | ❌ | **`246f38bc…`** (계정이 하나뿐 — 전 297만 행이 이 값) |
| name | text | | — | ❌ | 같은 place_id 의 가까운 날짜에서 (아래 2절) |
| category | text | | — | ❌ | 같은 방식 |
| visitor_reviews | integer | | — | ❌ | **NULL** (지어내지 않는다) |
| blog_reviews | integer | | — | ❌ | **NULL** |
| saves | integer | | — | ❌ | **NULL** |
| created_at | timestamptz | | `now()` | ❌ | 복원 시각 (= 복원 행 식별표) |

인덱스: `pkey(id)`, `(owner_id)`, `(keyword, checked_date)`. **유니크 제약은 pkey 뿐**이고 FK 는 `owner_id → profiles` 하나.
→ **스키마상 걸리는 것이 없다.** NOT NULL 인 keyword·checked_date 는 스냅샷에 있다.

## 2. 비는 칼럼 처리

### 이름·업종 — 같은 place_id 의 다른 날짜에서 채울 수 있다
대리 실험(멀쩡한 16일 10/10~10/25 를 "잃었다"고 가정):

| | |
|---|---:|
| 그 구간 행 | 419,597 |
| 같은 place_id 가 다른 날짜에도 있는 행 | 418,630 (**99.77%**) |
| 구간 안에만 나타난 매장의 행(채울 수 없음) | 967 (0.23%) |
| 17일 사이(10/25 ↔ 11/11) 이름이 바뀐 매장 | 33 / 9,026 (0.37%) |
| 〃 업종이 바뀐 매장 | 23 / 9,026 (0.25%) |

→ **약 99.8% 를 채울 수 있고, 채운 값이 실제와 다를 확률은 약 0.4%.**
규칙: 구간 **직전**(10/25 → 과거 순) 값을 먼저, 없으면 **직후**(11/11 → 이후 순). 어디에도 없으면 **NULL 그대로**.
이름·업종은 날마다 변하는 측정값이 아니라 매장 속성이라 채우기를 권하지만, **"지어내지 않는다"를 엄격히 적용해 NULL 로 둘 수도 있다**
— 아래 표처럼 화면은 옛 행의 이름을 쓰지 않아서 어느 쪽이든 화면은 같다. (결정 필요)

### 리뷰 수·저장수 — NULL 로 둔다
날짜마다 달라지는 값이라 다른 날짜에서 가져오면 지어내는 것이다. **NULL.**
참고: 정상 구간(10/15~10/25)에서도 **saves 는 18%(50,953 / 285,413행)가 원래 NULL** 이다 — 화면은 이미 매일 NULL 을 다루고 있다.

## 3. 화면·기능별 영향 — 코드로 점검

| 화면·기능 | 옛 행에서 쓰는 칼럼 | 복원 행(리뷰·저장수 NULL)일 때 | 판정 |
|---|---|---|---|
| **순위 추적 카드** (칸의 순위·▲▼) | rank | 순위·변동 정상 표시 | ✅ 완전 복구 |
| 〃 지표 상세(저장/리뷰/블로그) | saves, visitor_reviews, blog_reviews | `ptNum(null)` → **`-`**, `ptDelta` 는 한쪽이 null 이면 **빈칸** | ✅ 안전 ("저장 -", "리뷰 -") |
| 〃 '수집 안 됨' 판정 | 그날 **rank=1 행** 유무 | 스냅샷에 1위 행이 있으면 '수집됨' | ✅ (대조 스크립트가 쌍마다 확인) |
| **날짜 비교 탭** | 기준일의 **place_id → rank** 만 | 이름·리뷰는 **오늘 행**에서만 표시 | ✅ 완전 복구 |
| **SEO 분석** — 키워드별 최신 순위 | rank | 최신 날짜를 쓰므로 복원 행과 무관 | ✅ |
| 〃 리뷰 증가(7일/30일) | visitor_reviews | `filter(r => r.visitor_reviews != null)` 로 **NULL 행을 건너뜀** → 30일 기준이 10/25 로 잡힘(지금과 같음) | ✅ 안전, 단 **리뷰 추이는 복구 안 됨** |
| 〃 상위 매장 표 | 가장 최근 스냅샷 | 복원 행과 무관. null 은 `-` 처리 | ✅ |
| **임베드** | rank 만 | 12일 창 | ✅ |
| cpr-marketing-os 동기화 | place_id, keyword, rank, date | — | ✅ |
| 재현율 판정 도구 | place_id 집합 | — | ✅ |

**예전 사고와의 대조:** 과거 "null 이 화면에 그대로 찍힌" 건 **rank 가 NULL** 인 행이었다(지금은 `r.rank!=null` 로 걸러 낸다).
이번 복원 행은 **rank 가 있다** — 대조 스크립트가 rank 없는 행·범위 밖(1~300) 행을 세어 0 인지 확인한다.

**하나 발견한 것(이번 복원과 무관한 기존 동작):** 날짜 비교 탭의 `prFmt(n)` 은 `(Number(n)||0)` 이라
**리뷰 수가 NULL 이면 "0" 으로 찍는다.** 오늘 행에만 쓰여 복원 행은 여기로 안 들어가지만,
오늘 수집분에 NULL 이 있으면 "0" 으로 보인다. 고칠지는 따로 결정.

## 5. 대조 절차 (파일이 오면 — 읽기만)

도구: `scraper/tools/snapshot_recover_check.mjs` (DB 에 쓰지 않는다. 네이버 요청 없음)
```
node scraper/tools/snapshot_recover_check.mjs --in=<파일 또는 폴더> --truth=<DB 집계> --out=<복구 대상 jsonl>
```
1. **스냅샷 × 날짜 표**: 같은 날짜가 여러 스냅샷에 있을 때 행 수가 같은지(안정) — 다르면 어느 실행에서 변했는지 보인다.
2. **제외**: 오염 1,782쌍 + 이미 되살린 16쌍.
3. **날짜별 대조**: 남은 행 수 vs **2026-11-14 삭제 호출이 출력한 행 수**(−16쌍). 합 **132,926**.
   | 10/26 | 10/27 | 10/28 | 10/29 | 10/30 | 10/31 | 11/01 | 11/02 |
   |---:|---:|---:|---:|---:|---:|---:|---:|
   | 25,752 | 24,035 | 24,844 | 19,690 | 1,303 | 1,450 | 1,050 | 1,184 |
   | 11/03 | 11/04 | 11/05 | 11/06 | 11/07 | 11/08 | 11/09 | 11/10 |
   | 986 | 1,033 | 1,413 | 1,236 | 1,029 | 1,029 | 1,699 | 25,193 |
4. **쌍 단위 대조**: 수집 로그의 (날짜, 키워드)별 마지막 저장 행 수([log_pair_counts.json](restore-2026-11/log_pair_counts.json))와 비교 →
   없는 쌍 / 스냅샷에만 있는 쌍 / 행 수 다른 쌍을 이름으로 보고.
5. **충실도 검증**: 지금도 DB 에 멀쩡한 날짜(10/25, 11/11~11/13)를 스냅샷과 비교 — 행 수·순위 합·지문(md5)이 같으면
   "스냅샷 = 당시 DB" 가 증명된다.
6. **값 점검**: rank 없음 / 범위 밖 / place_id 없음 / 1위 행 없는 쌍.

**스크립트 자체 시험(2026-11-21):** 로그의 쌍별 행 수로 가짜 스냅샷을 만들어 돌렸다 → 제외 후 15일이 위 표와 **정확히 일치**,
일부러 뺀 11/03 은 "−986, 없는 쌍 19개" 로 잡혔다. 덤으로 **로그 − 제외 쌍 = 지워진 행 수** 가 날짜별로 한 행도 안 틀림을 다시 확인했다.

판정: 16일 모두 차이 0 → **완전 복구**. 아니면 어느 날짜·어느 쌍이 비는지 그대로 보고한다.

## 6. 넣는 방법 (승인 후 — 지금은 계획만)
- **날짜 하나 = 트랜잭션 하나.** 전용 함수 `restore_place_day(날짜, 행들, 예상 행 수)` 를 만들어 서버에서 날짜별로 부른다:
  그 날짜에 대상 쌍이 이미 있으면 거부, 넣은 행 수가 예상과 다르면 **예외 → 그 날짜 전체 롤백**. service_role 전용, 끝나면 drop.
- 이름·업종은 한 번 만든 조회 표(place_id → name, category)를 함수가 붙인다(place_id 인덱스가 없어 행마다 찾으면 느리다).
- 순서: **10/26 하루 시범** → 화면·기능에서 NULL 확인 → 나머지. 시각 22:30~05:30.
- 커밋된 날짜를 되돌려야 하면 `purge_place_pairs(날짜, 키워드들, 넣은 행 수, 사유)` — 가드(오늘 밤 적용)와 충돌하지 않는 유일한 삭제 경로.
- 복원 행 식별: `created_at` = 복원 시각, id 구간 기록, 리뷰·저장수 NULL.

## 7. 복구 뒤 유실로 남는 구간 (화면 상수 `PLACE_LOSS`)
완전 복구되면 **행이 하나도 없는 날짜는 없어진다.** 남는 "빈 칸"은 **오염이라 일부러 지운 1,782쌍**뿐이다
(10/29 87쌍, 10/30~11/09 하루 150~157쌍, 10/26·11/10 각 1쌍). 이건 유실이 아니라 **수집 오류로 버린 값**이라
문구가 달라야 한다. 대조 결과가 나오면 상수 범위(아마 `10/29~11/09`, 문구 "수집 오류로 제외")를 다시 정한다.
