# 배포 전 필수 점검 (blog-rank)

## 화면·렌더링 수정 시 실제 실행 검증 (2026-09-25 신설)
2026-09-25 사건: 블로그 진단을 3화면으로 재구성하면서 지운 요소(`#bdDetailSec`)를 심사 시작 함수가
계속 참조 → 버튼을 눌러도 두 번째 줄에서 예외가 나고 무음 중단, "심사 대기 중…"만 남음.
그때 회귀 확인은 "마커(요소·함수 이름) 존재 여부"만 봐서 통과로 판정했고, 기능은 전면 정지 상태였다.

**규칙**
1. 화면이나 렌더링을 건드린 배포는 **그 기능을 실제 입력으로 끝까지 1회 실행**한다.
   - 블로그 진단: 블로거 1명 심사를 **결과 표가 뜰 때까지** (또는 실패 사유가 뜰 때까지)
   - 플레이스 순위 추적 / 매장 블로그 순위: 키워드 1개 즉시조회가 **순위 또는 정상 미노출로 채워질 때까지**
   - 플레이스 SEO 분석 / 키워드 조합기: 리포트·조합 결과가 화면에 렌더될 때까지
2. 그 실행 결과 **스크린샷을 보고에 첨부**한다. 로그 문구만으로 갈음하지 않는다.
3. **마커 존재 확인만으로 "회귀 없음"이라고 쓰지 않는다.** 마커 검사는 보조 수단이며,
   "실행했다 / 결과가 나왔다"를 확인한 경우에만 회귀 없음이라고 적는다.
4. 정적 검사 필수 실행: `node scraper/tools/check_dom_refs.mjs index.html`
   — 코드가 참조하는 `getElementById` id가 마크업에 전부 존재하는지 확인한다(이 사건을 잡아내는 검사).

## 플레이스 즉시수집 연속 등록 테스트 (2026-09-04 신설)
연속 등록 동시 발사로 5/6 키워드가 조용히 실패했던 사건의 재발 방지.

1. 테스트 매장에 키워드 10개를 빠르게 연속 등록한다.
2. 합격 기준: 몇 분 안에 10개 전부 "순위 숫자" 또는 정상 "미노출(-)"로 채워질 것.
   - 실패가 "-"로 보이면 불합격 (실패는 반드시 "재시도 대기"로 표시돼야 함)
   - 오늘 칸이 "조회 중…" 상태에서 순차적으로 하나씩 채워지는지 확인 (동시 발사 금지)
3. 서버 로그 확인: `grep '\[place-search\]' /var/log/blog-rank-scraper/out.log | tail`
   — 요청이 겹치지 않고 순차 처리됐는지(대기포함 시간이 계단식) 확인.

## 자동화된 로직 검증 (로컬)
- 큐 동시성 테스트: index.html에서 ptCollectKeyword~ptPumpQueue 실코드 추출 + 모의 fetch로
  "최대 동시 요청=1, 전량 저장, 실패는 재시도 대기" 확인 (CRLF 주의: 추출 전 \r 제거)
- `node --check` scraper/*.mjs, scraper/src/*.js + index.html 인라인 스크립트 구문 검사
- `node scraper/tools/check_dom_refs.mjs index.html` — 없는 요소 참조 검사(0건이어야 통과)
- 큐 예외 처리 테스트: 정상·잘못된 입력·예외·무응답을 섞어 큐를 돌려 **실패가 있어도 끝까지 처리되고
  버튼이 풀리는지** 확인(무음 중단·영구 대기 방지)

## 배포 타이밍
- pm2 재시작(~20초 창) 중 사용자의 즉시조회 큐가 돌고 있으면 첫 패스가 일제 실패해
  "재시도 대기"가 한꺼번에 뜬다(2분 후 자동 재시도가 흡수). 가능하면 유휴 시간에 배포하고,
  배포 직후 "재시도 대기" 다발은 장애가 아니라 재시작 창 통과 흔적인지 로그(요청 처리 재개)로 먼저 확인.

## 상시 회귀 기준
- 기존 정상 키워드 순위(예: 부산 사직 맛집 43위대, 진주 상봉동 맛집 7위대)가 ±5 밖으로 틀어지면 원인 조사
- 스냅샷 저장 곳수가 300→두자릿수로 급감하면 축소 응답 의심 (failures.log·⚠ 로그 확인)
- 원격 상태 변경(배치 기동·재시작)은 실행 직후 로그의 "시작" 라인으로 즉시 검증
